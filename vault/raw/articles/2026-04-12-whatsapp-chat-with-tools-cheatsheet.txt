## Executive Summary
This document outlines the technical architecture of the Uber platform, focusing on the transition from high-latency polling systems to a real-time, push-based infrastructure. The system is designed to handle millions of concurrent connections, synchronize state between riders and drivers in near real-time, and ensure smooth UI performance despite variable network conditions.

---

## Part 1: Mobile Architecture (Client-Side)

The mobile client (Driver and Rider apps) focuses on efficient battery usage, low-latency connection termination, and predictive rendering to mask network instability.

### 1.1 Network Communication Layer
*   **Protocol:** **gRPC** (Bidirectional Streaming).
    *   *Evolution:* Originally used HTTP Polling (inefficient), then Server-Sent Events (SSE), and finally migrated to gRPC.
    *   *Benefit:* Allows messages to be sent from both client-to-server and server-to-client over a single persistent connection, reducing handshake overhead.
*   **Connection Termination:** **Edge Servers**.
    *   The app does not connect to a central data center (e.g., California). instead, it connects to the nearest geographical Edge Server (e.g., Frankfurt).
    *   *Impact:* Reduces Round Trip Time (RTT) significantly (e.g., from ~130ms to ~30ms), improving responsiveness on cellular networks (4G/5G).

### 1.2 Rendering & Smoothness (The "Phantom Car" Solution)
Real-time GPS updates are discrete and often delayed. To prevent cars from teleporting or "jumping" on the map, the client implements predictive logic.

*   **Dead Reckoning:**
    *   The app calculates where the driver *should* be based on their last known position, speed, and heading (vector direction).
    *   This fills the gaps between network packets (e.g., if packets arrive 20 seconds apart).
*   **Kalman Filters:**
    *   An algorithm used to smooth out the noise between the *predicted* position (Dead Reckoning) and the *actual* measured position when a network packet arrives.
    *   *Result:* The car marker glides smoothly along the road rather than snapping to coordinates.

### 1.3 Power Management
*   **Push-Based Architecture:** By removing the need for the client to constantly poll the server ("Is there a new ride?", "Where is the driver?"), the radio antenna on the device is used less frequently, significantly reducing battery consumption.

---

## Part 2: Server Architecture (Backend)

The backend handles the complexity of ingesting millions of location points, indexing them spatially, and determining *who* needs to receive updates.

### 2.1 Communication Infrastructure: RAMEN
**RAMEN (Realtime Asynchronous MEssaging Network)** is the proprietary service layer built to handle persistent connections.

*   **Function:** Maintains the persistent gRPC connections with millions of mobile devices.
*   **Reliability:** Guarantees **at-least-once delivery**. Even if a device temporarily disconnects, RAMEN ensures the message payload is delivered upon reconnection.
*   **Payload Management:** Acts as the pipe. It receives payload instructions from the business logic layer (Fireball/Gateway) and pushes them to the specific user connection.

### 2.2 Event Decisioning: Fireball
**Fireball** is the microservice responsible for the "intelligence" of the push system. It decides *when* and *what* to push.

*   **Change Detection:** It listens to event streams (driver location updates, ride acceptance, status changes).
*   **Diffing Logic:** Fireball compares the new state against the previous state.
    *   *Example:* If a driver moves 1 meter, it might not be worth a push. If they move 50 meters, Fireball triggers an update.
*   **Optimization:** Reduces unnecessary network traffic by filtering out redundant or insignificant data before it reaches the transmission layer.

### 2.3 Spatial Indexing: H3 (Hexagonal Hierarchical Spatial Index)
To match riders with drivers efficiently, the server cannot calculate the distance between a rider and *every* driver globally ($O(N)$ complexity).

*   **Spatial Partitioning:** The world is divided into a grid of hexagons.
*   **Why Hexagons?**
    *   Unlike squares, hexagons reduce **Corner Bias**. The distance from the center of a hexagon to the center of all six neighbors is uniform.
    *   Square grids suffer from diagonal neighbors being further away than orthogonal neighbors.
*   **The kRing Algorithm:**
    *   To find nearby drivers, the server queries the Rider's hexagon and the surrounding "rings" of hexagons (k-steps away).
    *   *Efficiency:* Reduces search complexity to $O(k^2 + m)$, where $k$ is the search radius and $m$ is the number of drivers in that small area.

### 2.4 Data Aggregation: API Gateway
*   Before a push occurs, the API Gateway gathers all necessary context (User Locale, Device OS, Trip Metadata) from downstream microservices to form a complete payload.
*   This payload is handed to RAMEN for delivery.

---

## Part 3: Data Flow Summary

### Scenario: A Driver is en route to a Rider

1.  **Ingestion (Mobile -> Edge):** The Driver's app sends a GPS coordinate via **gRPC** to the nearest **Edge Server**.
2.  **Indexing (Server):** The backend maps this coordinate to a specific **H3 Hexagon**.
3.  **Decision (Fireball):** Fireball detects the location change. It determines that Rider X is subscribed to this Driver's location. It calculates if the change is significant enough to warrant an update.
4.  **Dispatch (RAMEN):** Fireball sends the payload to **RAMEN**. RAMEN locates the open socket for Rider X.
5.  **Delivery (Edge -> Mobile):** The update is pushed to Rider X's device.
6.  **Smoothing (Mobile):** Rider X's app receives the coordinate. The **Kalman Filter** blends this new point with the current **Dead Reckoning** prediction to smoothly animate the car icon on the map.
