# Running Multiple Instances of React Native in Sandbox

## Summary
This source captures Callstack’s public article introducing `@callstack/react-native-sandbox`. It is best understood as React Native super-app and plugin-runtime architecture material: the article argues that Module Federation and Re.Pack solve bundle modularity, but not runtime isolation, and positions `react-native-sandbox` as the missing layer for running multiple isolated React Native instances with capability whitelisting, bounded messaging, and crash containment. [src-2026-05-20-002]

## Key Claims
- The article distinguishes code delivery modularity from runtime isolation, arguing that independently loaded React Native bundles can still interfere with each other unless they are isolated at runtime. [src-2026-05-20-002]
- `react-native-sandbox` is presented as a way to run multiple fully isolated React Native instances inside one host app, with each sandbox owning its own JavaScript runtime. [src-2026-05-20-002]
- Capability exposure is intentionally constrained through an `allowedTurboModules` whitelist, which the article frames as a key security boundary for third-party or experimental code. [src-2026-05-20-002]
- Communication between sandbox and host is intentionally narrowed to a message-passing API built around `postMessage` and `setOnMessage`. [src-2026-05-20-002]
- The article’s demo is designed to show fault containment directly: destructive plugin behavior that would destabilize the host app when run normally is contained when run inside the sandboxed instance. [src-2026-05-20-002]
- The current platform boundary is explicit: the article says iOS is supported at the moment, and it acknowledges overhead from running multiple JS runtimes. [src-2026-05-20-002]
