# React Native performance tactics: Modern strategies and tools

## Summary
This source captures Sentry’s React Native performance article by Simon Grimm. It is best understood as a modern React Native performance workflow: reduce startup work, profile re-renders, protect the JavaScript thread, use better list primitives, structure state carefully, and instrument real user performance through Sentry profiling, tracing, and spans. [src-2026-05-30-001]

## Key Claims
- The article’s main process claim is to profile first and optimize second, using React Native DevTools, Expo tooling, Flashlight, and Sentry rather than guessing where the bottleneck is. [src-2026-05-30-001]
- Startup performance is framed around Time to Interactive: defer heavy initialization, lazy load route code with Expo Router, and inspect bundle weight with Expo Atlas. [src-2026-05-30-001]
- React-level performance work includes identifying unnecessary re-renders, enabling React Compiler where available, and cleaning up memory leaks from listeners, intervals, WebSockets, and uncancelled async work. [src-2026-05-30-001]
- The article treats 60 FPS as a practical product threshold, with guidance to avoid blocking the JS thread and to consider chunking, concurrent React APIs, Reanimated 4, and Worklets for expensive work. [src-2026-05-30-001]
- For list and state performance, it recommends FlashList or LegendList over naive `ScrollView` mapping, lightweight `renderItem` paths, immutable updates, split contexts, and fine-grained state libraries such as Jotai or Zustand when needed. [src-2026-05-30-001]
