# Naming Complex Conditions and Magic Numbers

## Summary
This source refines the readability side of frontend code quality by arguing that non-trivial conditions and unexplained numeric literals should usually be named so the code communicates intent directly. [src-2026-04-14-004]

## Key Claims
- Inline nested conditions reduce readability because the reader must hold too many contexts in mind at once, especially when anonymous functions and boolean expressions are stacked together. [src-2026-04-14-004]
- Introducing names such as `isSameCategory` or `isPriceInRange` can make intent clearer without changing the underlying behavior. [src-2026-04-14-004]
- Naming is especially helpful when logic is complex, reusable, or worth unit testing, but may be unnecessary for very simple one-off logic. [src-2026-04-14-004]
- Unnamed numeric literals are “magic numbers” that hide intent, and promoting them into constants such as `ANIMATION_DELAY_MS` makes code easier to understand and safer to modify. [src-2026-04-14-004]
