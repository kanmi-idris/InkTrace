# The Go-To Guide for Understanding Keyboards in React Native (Part 1)

## Summary
This source captures Margelo’s deep dive on React Native keyboard handling. It is best understood as platform-behavior and interaction-polish guidance: iOS provides scheduled keyboard animations, modern Android provides per-frame inset changes, Android 15 forces edge-to-edge behavior for SDK 35 targets, and reliable React Native keyboard UI needs to normalize those models into shared animated values rather than relying on the stock `KeyboardAvoidingView`. [src-2026-05-28-001]

## Key Claims
- The article’s core platform claim is that iOS and Android expose fundamentally different keyboard primitives: iOS gives a final frame plus animation timing, while Android’s modern edge-to-edge model requires app-driven layout from insets and per-frame animation callbacks. [src-2026-05-28-001]
- Android 15 is a key breaking point because edge-to-edge is forced for apps targeting SDK 35, which undermines older assumptions that `adjustResize` will keep layouts away from the keyboard automatically. [src-2026-05-28-001]
- React Native’s built-in `KeyboardAvoidingView` is framed as iOS-friendly but structurally weak on Android because it lacks per-frame inset tracking and reacts too late for synchronized keyboard animation. [src-2026-05-28-001]
- `react-native-keyboard-controller` is presented as the practical replacement because it bridges iOS scheduled animations and Android per-frame insets into common animated values, including older Android compatibility behavior. [src-2026-05-28-001]
- The article’s component-selection model is especially useful: use `KeyboardAvoidingView` to make bounded layouts roomier, `KeyboardAwareScrollView` to keep focused inputs and carets visible in scrollable forms, and `KeyboardStickyView` for footers or toolbars that should translate with the keyboard without resizing the whole screen. [src-2026-05-28-001]
