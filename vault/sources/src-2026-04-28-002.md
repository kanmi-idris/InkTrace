# TanStack Start RSC use case for CDN-cached content sites

## Summary
This source captures the supplied transcript of a video explaining a specific React Server Components use case in TanStack Start. The central claim is that RSCs are most valuable as a specialized tool for pages where different regions need different cache behavior and where interactive client code can be loaded only when the server-rendered payload actually references it. [src-2026-04-28-002]

## Key Claims
- The transcript explicitly rejects a one-size-fits-all framing for RSCs and instead presents them as a highly specialized tool for certain site architectures. [src-2026-04-28-002]
- The main example is a CDN-cached content site where the route as a whole is easy to cache, but a region such as a trending sidebar needs much more frequent cache invalidation than the rest of the page. [src-2026-04-28-002]
- In the shown TanStack Start implementation, a client-side wrapper requests an RSC payload from a GET server function so the CDN can cache that response independently. [src-2026-04-28-002]
- The example uses TanStack Start’s low-level RSC API through `renderServerComponent`, with the client receiving flight data rather than a JSON payload. [src-2026-04-28-002]
- The transcript argues that JSON is functionally possible but less attractive because the client must still ship and execute all rendering code, whereas RSC flight data can be inserted into the existing VDOM with less client-side rendering work. [src-2026-04-28-002]
- A second claimed benefit is bundle deferral: if an RSC references an interactive `"use client"` component, the browser can fetch only that component’s JavaScript instead of receiving a large up-front bundle containing every possible interactive component. [src-2026-04-28-002]
- The speaker generalizes the idea beyond content sites to dashboards with many optional widgets, where only a small subset of client-side interactivity may be needed per user. [src-2026-04-28-002]
