# CSS vs. JavaScript

## Summary
This source captures Josh W. Comeau’s article on CSS versus JavaScript animation performance. It is best understood as frontend animation performance guidance: CSS keyframes, Web Animations API based tools, and JavaScript animation loops may animate the same properties, but their behavior differs under main-thread pressure, synchronization requirements, and bundle-cost constraints. [src-2026-05-30-004]

## Key Claims
- The article argues that CSS animations are often smoother not because JavaScript math is inherently too slow, but because CSS transitions and keyframes can run away from the main JavaScript thread. [src-2026-05-30-004]
- JavaScript `requestAnimationFrame` loops can freeze when the main thread is busy because they compete with framework updates, fetch parsing, and other application work. [src-2026-05-30-004]
- Motion is presented as an important exception among JavaScript-facing animation tools because it uses the Web Animations API, allowing some animations to run through the browser’s lower-level animation engine rather than a main-thread loop. [src-2026-05-30-004]
- The article distinguishes smoothness from synchronization: an elapsed-time based loop can snap back into sync after dropped frames, while some frame-progress based library behavior may avoid snapping but drift from a fixed-duration schedule. [src-2026-05-30-004]
- Its tool-selection rule is pragmatic: use native CSS when possible, use libraries when they unlock genuinely new animation capabilities, and avoid libraries that only wrap basic CSS transitions in JavaScript. [src-2026-05-30-004]
