# Livestreaming Trilemma: HLS, WebRTC, MOQ

Blog article from Software Mansion exploring the historical tension in livestreaming protocol design and how Media over QUIC (MoQ) aims to dissolve fundamental architectural constraints.

## Central Thesis

Live video streaming presents a trilemma: builders must choose two of three desirable properties:
- **Scale**: How many concurrent viewers can infrastructure support cost-effectively?
- **Latency**: How quickly do viewers experience the stream after capture?
- **Cost**: What operational expense is required for delivery?

HLS optimizes for scale and cost (via CDN infrastructure) but sacrifices latency (10-30 seconds). WebRTC optimizes for latency (sub-200ms) but sacrifices cost and scale (Selective Forwarding Unit overhead grows per viewer). Media over QUIC attempts to optimize all three simultaneously through a publish-subscribe relay architecture.

## Historical Evolution

1. **RTMP** (Flash era): Worked but didn't scale, relied on deprecated browser plugins
2. **HLS/DASH** (late 2000s onward): Leverage existing HTTP/CDN infrastructure, enables mass-scale streaming, introduces latency penalty
3. **WebRTC** (video conferencing adapted): Provides sub-200ms latency and synchronization, at cost of per-viewer SFU server resources
4. **Low-Latency HLS** (incremental improvement): Reduces latency to 3-5 seconds via CMAF chunking, maintains HLS cost/scale model
5. **Media over QUIC** (emerging standard): Targets simultaneous achievement of all three properties

## Key Architectural Distinction

**HLS Model**: Publisher → central origin server → CDN edge cache → many subscribers (pull-based, stateless per subscriber)
- Cost efficiency: marginal cost of additional viewer ≈ zero (cache already exists)
- Latency penalty: chunking and buffering inherent to file-based model

**WebRTC Model**: Publisher ↔ SFU ↔ subscriber (peer connection simulation, stateful per subscriber)
- Latency advantage: real-time bidirectional protocol reduces buffer requirements
- Cost penalty: SFU must maintain encrypted connection state for every viewer, parse RTP per viewer, react to each viewer's bandwidth → CPU/memory intensive → requires cascaded custom SFU networks rather than commodity CDN backbone

**MoQ Model**: Publisher → relay (pub/sub) → subscriber (named paths, subscriber-driven subscription)
- Combines: CDN-like scalability (relay can distribute without per-subscriber state complexity) + WebRTC-like latency (QUIC transport, real-time semantics)
- Key innovation: relays can be placed in existing CDN infrastructure, path-based subscription model doesn't require central server to know all subscribers

## Emerging Use Cases Requiring All Three

Live events where latency creates material impact:
- Online betting (5-second lag = line already moved by the time viewer acts)
- Live shopping (early viewers see items first)
- Watch parties with real-time group reaction (requires synchronization)
- Live sports and concerts (audience needs to feel synchronized, not fractured by latency)

## Industry Signals

- **Status**: IETF working group draft with multiple running implementations
- **Participants**: Meta, Google, Cisco, Akamai attending standardization meetings
- **Momentum**: Streaming startups racing to ship first production deployments
- **Sentiment**: Genuine engineering excitement (not dismissal of "yet another protocol")

## Technical Foundation

- Built on QUIC (HTTP/3 transport layer)
- Standardized through same process as HTTP and TLS
- Not a codec or player replacement
- Solves "what both HLS and WebRTC cannot do together" rather than replacing either
