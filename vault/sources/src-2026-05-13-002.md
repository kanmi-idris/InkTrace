# Understanding useNativeState in Expo UI

## Summary
This source captures Beto’s article on `useNativeState` in Expo UI. It is best understood as a practical performance note and mental-model guide: `useNativeState` is framed as a native-memory shared-state mechanism that lets SwiftUI or Compose-backed UI read and write fast-changing values without routing each update through the JavaScript thread, especially for text input and other high-frequency controls. [src-2026-05-13-002]

## Key Claims
- The article says Expo SDK 56 introduces `useNativeState` in Expo UI. [src-2026-05-13-002]
- The visible preview describes the hook as a lightweight reference to a value stored in native memory rather than ordinary React state owned by the JS thread. [src-2026-05-13-002]
- The article’s performance framing centers on controlled text input: it argues that the usual event-to-JS-state-to-rerender-to-native-prop loop is what makes fast typing feel sluggish. [src-2026-05-13-002]
- The article presents `.value` as the direct read/write API and warns that the hook should be seeded with a constant initial value rather than a changing render-time value. [src-2026-05-13-002]
- It also positions worklet callbacks as the right escape hatch when UI-thread change handling is needed without bouncing through the JS thread. [src-2026-05-13-002]
- The hook is described as returning a `SharedObject`, meaning the fast-changing value itself stays in native memory while JavaScript only holds a handle to it. [src-2026-05-13-002]
