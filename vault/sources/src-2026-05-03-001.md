# Nigerian Fintech Money Modeling: Kobo vs Decimals

## Summary
This source captures a user-supplied money-modeling argument plus rebuttal. Its value is not a single definitive schema rule, but a practical systems-design tension: settlement, reconciliation, and payment flows strongly benefit from integer minor units, while some retail, inventory, or fractional-allocation domains may still require higher internal precision before final rounding. [src-2026-05-03-001]

## Key Claims
- The main post argues that storing money in decimal or float forms can create real ledger drift, and recommends storing Nigerian naira amounts strictly as integer kobo values instead. [src-2026-05-03-001]
- It recommends pushing decimal formatting to display boundaries only, wrapping amounts in a typed money abstraction, and making rounding rules explicit per use case rather than implicit in arithmetic. [src-2026-05-03-001]
- It also argues that reconciliation with providers or settlement-bank exports is safer when internal records use the same integer minor units those systems usually expose. [src-2026-05-03-001]
- The follow-up commentary pushes back by arguing that some domains need more than two decimal places internally, especially when cost allocation or profit exists below the normal display precision of the currency. [src-2026-05-03-001]
- Taken together, the source suggests a layered rule rather than a universal one: use integer minor units for externally settled money movements when possible, but distinguish that from internal accounting or inventory calculations that may need higher-precision intermediate values. [src-2026-05-03-001]
